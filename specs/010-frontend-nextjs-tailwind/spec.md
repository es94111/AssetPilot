# 功能規格：前端框架遷移至 Next.js + Tailwind CSS v4

**功能分支**：`010-frontend-nextjs-tailwind`  
**建立日期**：2026-05-03  
**狀態**：就緒（待實作）  
**輸入**：使用者描述：「將前端程式碼改成 Next.js + Tailwind CSS v4」

## 釐清記錄

### Session 2026-05-03 (第一輪)

- Q: 各功能頁面應採用哪種 Next.js 渲染策略？ → A: 動態頁面（含使用者資料）採用 SSR，靜態頁面（登入、說明）採用 SSG。
- Q: 遷移後的部署目標環境為何？ → A: 自管 VPS 或 Docker 容器，採用 Next.js Standalone 模式，維持現有 Node.js 執行環境。
- Q: Express Session 遷移至 Next.js 後，Session 管理機制為何？ → A: 採用 Cookie-based Session（`iron-session` 或相似方案），加密 Cookie 儲存 Session，無需外部 Session Store，行為與現有 Express Session 最接近。（→ 實際決策：保留現有 `jsonwebtoken` JWT httpOnly Cookie，無需 iron-session，見 FR-003）
- Q: 遷移期間的功能範圍邊界為何？ → A: 嚴格限定——框架遷移期間不新增任何功能、不重新設計 UI 視覺、不修改資料庫結構；所有改善列為後續獨立請求。
- Q: Next.js API Routes 中的資料庫連線生命週期管理方式為何？ → A: 非生產環境應用，不接觸生產資料庫；採用最簡單的連線方式即可，無需考慮高並發連線池管理。

### Session 2026-05-03 (第二輪)

- Q: 應用程式是否有伺服器端外部 API 呼叫（如 TWSE 股價抓取）需移植？ → A: 有，所有現有伺服器端外部 API 呼叫必須原樣移植至 Next.js API Routes，行為不得改變。
- Q: 遷移後頁面 URL 路徑是否需要完全一致？ → A: 是，URL 路徑必須與現有版本完全相同，不允許任何路徑變更，不提供重新導向。

## 使用者情境與測試 *(必填)*

### 使用者情境 1 — 現有功能完整保留（優先順序：P1）

使用者登入後，能夠順暢使用所有現有功能（帳戶管理、交易記錄、預算、統計報表、分類管理等），介面行為與遷移前完全一致，不需要重新學習操作方式。

**為何為此優先順序**：使用者不應感受到底層框架更換帶來的任何功能退化。若任何現有功能在遷移後失效，本次遷移即為失敗。

**獨立測試**：可針對每個現有功能頁面（帳戶、交易、分類、預算、報表、股票投資、資料匯出匯入）逐一驗證其與遷移前行為一致，每頁均可獨立驗收。

**驗收情境**：

1. **Given** 使用者已登入並進入任意功能頁面，**When** 使用者執行既有操作（新增、編輯、刪除、篩選等），**Then** 結果與遷移前完全相同，且無錯誤訊息出現。
2. **Given** 使用者未登入，**When** 使用者試圖訪問受保護頁面，**Then** 自動導向登入頁，行為與遷移前一致。
3. **Given** 使用者在任意頁面，**When** 頁面發生路由導航，**Then** 瀏覽器歷史記錄正常運作（上一頁、下一頁按鈕有效）。

---

### 使用者情境 2 — 頁面載入效能提升（優先順序：P2）

使用者感受到頁面初次載入速度明顯加快，尤其在首次訪問時不再需要等待整個單頁應用程式完整下載才能看到內容。含使用者資料的功能頁面採用 SSR 在伺服器端預先渲染；登入等靜態頁面採用 SSG 預先生成，確保資料安全性的同時最大化載入效能。

**為何為此優先順序**：SSR/SSG 是遷移的核心效益之一，此效益應在遷移完成後實際可量測。

**獨立測試**：可對任意頁面使用 Lighthouse 或 WebPageTest 量測初次載入的 LCP（最大內容繪製）時間，與遷移前數據比較。

**驗收情境**：

1. **Given** 使用者首次訪問應用程式，**When** 頁面完成載入，**Then** 使用者在後端資料尚未全部就緒前即可看到頁面基礎結構（骨架畫面或初始內容）。
2. **Given** 使用者在行動裝置上訪問，**When** 頁面完成載入，**Then** 響應式版面與桌面版功能對等，且 LCP 指標在合理範圍內。
3. **Given** 使用者未登入，**When** 訪問登入頁，**Then** 頁面由 CDN 或預先生成的靜態檔案直接提供，無需等待伺服器動態渲染。

---

### 使用者情境 3 — 樣式視覺一致性（優先順序：P3）

使用者在遷移後看到的介面視覺風格與現有版本保持高度一致，Tailwind CSS v4 的工具類別替換不產生意外的樣式破損。

**為何為此優先順序**：樣式遷移風險相對較低，可逐頁驗收，屬於技術性細節工作。

**獨立測試**：可對每個頁面進行視覺截圖比對（遷移前 vs. 遷移後），確認佈局、色彩、間距無明顯差異。

**驗收情境**：

1. **Given** 遷移完成後，**When** 使用者訪問任意頁面，**Then** 所有 UI 元素（按鈕、表單、表格、圖表、導覽列）的視覺呈現與功能行為均正常。
2. **Given** 使用者在不同螢幕尺寸下使用，**When** 檢視響應式斷點，**Then** 版面斷點行為與遷移前一致。

---

### 邊界情境

- 若後端 API 回傳錯誤，前端應顯示與遷移前一致的錯誤提示。
- 若使用者瀏覽器不支援特定 JavaScript 功能，應有合理的降級處理（fallback）。
- 若網路連線中斷，應用程式應維持與現有版本相同的離線行為。
- 深色模式（若現有版本支援）應在遷移後繼續正常運作。
- SSR 頁面在伺服器端發生錯誤時，應顯示友善的錯誤頁面，不得暴露伺服器內部資訊。

## 需求 *(必填)*

### 功能需求

- **FR-001**：遷移後的前端必須呈現並支援現有所有功能頁面：帳戶管理、交易記錄、分類管理、預算管理、統計報表、股票投資、資料匯出匯入。
- **FR-002**：所有現有後端 API 端點的呼叫方式（路徑、請求格式、回應格式）必須在遷移後維持相容，後端 API 契約不得因前端遷移而改變。
- **FR-003**：使用者身份驗證流程（登入、登出、受保護路由）必須在遷移後完整保留，不得降低現有安全性。身份驗證機制保留現有 `jsonwebtoken` JWT，儲存於 httpOnly Cookie（Cookie 名稱 `token`），無狀態設計無需外部 Session Store。切換當下現有 Cookie 因格式不相容而失效，使用者需重新登入一次（此為可接受的一次性中斷）。
- **FR-004**：客戶端路由導航必須支援瀏覽器歷史記錄（上一頁、下一頁）及書籤功能。
- **FR-005**：所有現有表單驗證邏輯必須在遷移後維持相同行為（驗證規則、錯誤訊息顯示位置）。
- **FR-006**：現有資料視覺化元件（圖表、統計圓餅圖、趨勢線等）必須在遷移後正常渲染。
- **FR-007**：遷移後的應用程式必須通過現有所有自動化測試（如有），並能在本地開發環境中正常啟動。
- **FR-008**：現有 Express 後端的 API 路由必須逐步移入 Next.js API Routes，最終由單一 Next.js 應用程式同時提供前端頁面與後端 API 服務，取代原有的 Express 伺服器。所有現有伺服器端外部 API 呼叫（包含 TWSE 等第三方股價資料抓取）必須一併移植，行為不得改變。
- **FR-009**：遷移採一次性完整策略：在新分支中完整重建整個應用程式（前端頁面 + 後端 API），完成驗收後一次切換至新版本，不保留新舊並存的過渡期。
- **FR-010**：含使用者個人資料的功能頁面（帳戶、交易、分類、預算、報表、股票）必須採用 SSR（伺服器端渲染），確保資料不暴露於公開快取；登入等靜態內容頁面採用 SSG（靜態生成）。

### 關鍵實體

- **頁面/路由**：現有所有功能頁面，遷移後 URL 路徑必須與現有版本完全相同（不允許路徑變更，不提供重新導向）。
- **API 呼叫層**：前端與後端之間的資料交換層，遷移後必須維持相同的資料契約。
- **身份驗證狀態**：JWT Token 狀態管理——以 httpOnly Cookie（名稱 `token`）傳遞 JWT，`middleware.js` 負責驗證；遷移後行為必須與現有版本一致。
- **UI 元件庫**：現有的自定義元件（按鈕、表單、表格、圖表等），在遷移中需一一對應重建。

## 成功標準 *(必填)*

### 可量測成果

- **SC-001**：遷移完成後，100% 的現有功能頁面可正常訪問且操作結果與遷移前一致（無功能退化）。
- **SC-002**：功能頁面（SSR）初次載入的 LCP 比遷移前縮短至少 20%；靜態頁面（SSG）LCP 縮短至少 40%（以 Lighthouse 或 WebPageTest 量測）。
- **SC-003**：所有頁面在主流瀏覽器（Chrome、Safari、Firefox 最新版）與常見螢幕尺寸（手機、平板、桌面）下均可正常顯示與操作。
- **SC-004**：本地開發環境啟動時間不超過 30 秒，且支援熱更新（Hot Module Replacement）以提升開發效率。
- **SC-005**：遷移完成後，不新增任何已知安全漏洞（通過現有安全性驗證流程）。

## 假設

- Express 後端邏輯（路由處理、資料庫存取、身份驗證）將整體移入 Next.js API Routes；現有資料庫結構不變。
- 身份驗證機制保留現有 `jsonwebtoken` JWT，以 httpOnly Cookie（名稱 `token`）傳遞，驗證邏輯從 Express 中介層移至 `lib/auth.js` + `middleware.js`；切換當下現有 Cookie 因格式不相容而失效，使用者需重新登入一次（可接受的一次性中斷）。
- 遷移在單一新分支完整進行，不需要維護雙軌部署，切換後即廢棄舊版程式碼。
- 部署環境為自管 VPS 或 Docker 容器，使用 Next.js Standalone 模式（`next build` 產生 `.next/standalone`，以 `node .next/standalone/server.js` 啟動），取代原有 `node server.js`（Express）；PM2 或 Docker 等程序管理工具維持不變。
- Tailwind CSS v4 的設定方式（零配置為主）與現有 CSS 架構可合理轉換，不存在重大相容性障礙。
- 現有第三方圖表套件（如 Chart.js）與 Next.js + React 環境相容，遷移中無需替換。
- 遷移後仍維持繁體中文（zh-TW）作為唯一介面語言。
- 視覺設計以保留現有風格為目標，不進行視覺重新設計（如需視覺更新，列為獨立功能請求）。
- 此次遷移嚴格限定於框架替換：不新增功能、不修改資料庫結構、不重新設計 UI；任何遷移期間發現的改善機會，記錄為後續獨立任務處理。
- 本應用程式為非生產環境用途，不接觸生產資料庫；資料庫連線管理採用最簡單可行的方式，無需連線池或高並發優化。
